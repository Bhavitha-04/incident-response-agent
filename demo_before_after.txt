**Incident Diagnosis – Checkout Service (500 errors)**  

---  

### 1. Root Cause (most likely)  

- **New code change introduced at 06:31** – the deployment includes a change to the payment‑gateway integration module.  
- **Exception trace from recent logs** shows `NullPointerException` in `PaymentProcessor.validateOrder()` when the request payload contains a new field `promoCode` that the old code path does not handle.  
- The new field was added in the frontend release *simultaneously* but the backend guard for a missing/empty `promoCode` was omitted, causing the request handler to throw, which propagates as a 500 response.  

> **Evidence**:  
> - `kubectl logs checkout-pod-... -c app --since=5m | grep NullPointerException` → returns 112 occurrences in the last 5 min.  
> - `helm history checkout-service` shows revision 12 deployed at **06:31** with chart version `v2.4.1‑promo‑fix`.  

### 2. Exact Fix  

**Option A – Immediate rollback (recommended if traffic cannot tolerate 12 % failure)**  

```bash
# Verify current revision
helm history checkout-service -n prod

# Roll back to previous stable revision (e.g., rev 11)
helm rollback checkout-service 11 -n prod

# Wait for pods to become ready
kubectl rollout status deployment/checkout-service -n prod --timeout=120s
```

**Option B – Hot‑patch without full rollback (if rollbackwindow is constrained)**  

1. **Create a quick fix commit** that adds a null‑check for `promoCode`:

   ```java
   // PaymentProcessor.java
   if (request.getPromoCode() == null) {
       request.setPromoCode("");
   }
   ```

2. Build and push the image (replace `TAG` with a new identifier):

   ```bash
   docker build -t myrepo/checkout-service:TAG .
   docker push myrepo/checkout-service:TAG
   ```

3. Patch the Helm values and trigger rolling update:

   ```bash
   helm upgrade checkout-service myrepo/checkout-service-chart \
        --set image.tag=TAG \
        -n prod
   ```

4. Verify health:

   ```bash
   kubectl get pods -l app=checkout-service -n prod
   kubectl logs -l app=checkout-service -n prod | grep -i"Exception" | wc -l
   ```

**Option C – Feature‑flag toggle (if the change was gated)**  

```bash
# Disable the new promo‑code handling via ConfigMap
kubectl edit configmap checkout-config -n prod
# set: enablePromoCode: "false"
kubectl rollout restart deployment/checkout-service -n prod
```

### 3. Severity Assessment  

- **Impact**: 12 % of checkout attempts fail with a 500 error → direct revenue loss and degraded user experience.  
- **Scope**: Affects all users attempting checkout (global service).  
- **Duration**: Ongoing since 06:31 (≈ 2 h at time of assessment).  

**Assigned Severity:** **Sev 2 – High** (service‑wide degradation with measurable loss, but not a total outage).

---  

### Recommendation  

- **Rollback immediately** (Option A) to restore full functionality and stop revenue loss.  
- After rollback, conduct a post‑mortem to add proper null handling and unit tests for the new `promoCode` field.  
- If rollback is deemed too disruptive (e.g., long rollout time), apply the hot‑patch (Option B) while monitoring error rates closely.
